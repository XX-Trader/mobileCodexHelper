# 聊天附件查看器改造方案

## 1. 文档目的

这份文档用于定义聊天记录中“图片、Markdown 文件、日志文件及其他附件”的查看与下载方案，目标是先把范围、边界、技术取舍和实施顺序对齐，再进入实现。

本次方案只解决“聊天附件如何在站内查看、下载、打开”的问题，不扩展到完整文档管理系统，也不尝试一次性支持所有二进制文件的富预览。

## 2. 已确认需求

用户已经明确了以下需求：

1. 发送到聊天中的图片，必须在聊天记录里有可见信息，最好直接显示缩略图。
2. 点击图片后，不再新开网页，而是在站内打开图片查看器。
3. Markdown 文件要支持：
   - 在站内查看
   - 下载
   - 在新窗口打开，且格式正常
4. 日志文件要支持：
   - 在站内查看
   - 下载
5. 用户希望“文件尽量统一处理”，不要为每种文件单独做完全割裂的交互。

## 3. 核心结论

结论只有一条：

> 统一入口可以，但不能完全不区分文件类型。

原因很直接：

1. 图片需要查看器能力，不是文本渲染。
2. Markdown 需要按 Markdown 语义渲染，而不是纯文本。
3. 日志和普通文本文件适合文本查看器，但必须考虑大文件保护。
4. zip、sqlite、pdf、docx、exe 这类二进制文件不能可靠地按文本直接预览。

因此推荐方案是：

> “统一附件查看器入口 + 按能力分流渲染”

前端统一点开一个站内附件查看器，但查看器内部按以下四类决定如何展示：

1. `image`
2. `markdown`
3. `text`
4. `unsupported`

## 4. 改造目标

### 4.1 产品目标

1. 用户发送图片后，聊天记录里能直接看到缩略图。
2. 用户点击图片后，站内弹出图片查看器，不新开网页。
3. 用户点击 Markdown 文件后，站内弹出 Markdown 预览器。
4. Markdown 预览器提供“下载”和“新窗口打开”。
5. 用户点击日志文件或普通文本文件后，站内弹出文本查看器。
6. 文本查看器提供“下载”。
7. 未知或不支持预览的文件，至少能稳定下载。

### 4.2 工程目标

1. 复用当前已有的 `ChatAttachment` 数据结构和附件上传链路。
2. 复用已有 Markdown 渲染能力，避免引入新依赖。
3. 统一站内查看器容器，避免图片、Markdown、文本各做一套完全独立弹层。
4. 对大文件预览增加保护，避免前端卡死。
5. 保持后端附件访问的目录隔离与权限边界。

## 5. 非目标

本轮不做以下内容：

1. 不做通用二进制文件在线预览平台。
2. 不做 Office / PDF / SQLite 的深度解析预览。
3. 不做附件全文索引或全文搜索。
4. 不做日志高亮规则编辑器。
5. 不做跨会话附件收藏或长期存档能力。

## 6. 当前状态

当前链路已经具备以下基础能力：

1. 聊天输入框已经支持图片和普通附件的采集、粘贴、拖拽、上传。
2. 聊天消息已经能携带 `ChatAttachment` 元数据。
3. 后端已经有临时附件上传与预览接口：
   - `POST /api/projects/:projectName/chat-attachments`
   - `GET /api/projects/:projectName/chat-attachments/content`
4. 消息列表里已经能显示附件卡片，但当前点击仍然主要依赖 `window.open(...)`。

也就是说，本次不是从零开始，而是在“附件已可发送”的基础上，把“附件可查看”补完整。

## 7. 推荐交互方案

## 7.1 统一入口

用户在聊天记录中点击附件，不直接新开网页，而是统一进入站内附件查看器。

查看器推荐使用弹层或全屏面板，优先级如下：

1. 移动端：全屏查看器
2. 桌面端：大尺寸 Modal / Drawer

统一查看器头部提供：

1. 文件名
2. 文件类型或 MIME
3. 下载按钮
4. 新窗口打开按钮（仅对 Markdown 或明确需要的可预览文件开放）
5. 关闭按钮

## 7.2 图片

图片在聊天记录中的展示方式：

1. 用户消息内直接渲染缩略图
2. 点击缩略图进入图片查看器

图片查看器能力：

1. 原图查看
2. 缩放
3. 适应屏幕
4. 下载
5. 多图时支持左右切换

明确要求：

1. 不再使用新标签页查看图片
2. 不依赖浏览器原生打开图片页

## 7.3 Markdown 文件

Markdown 文件在聊天记录中展示为文件卡片，不强行内嵌全文。

点击后行为：

1. 站内打开 Markdown 预览器
2. 默认按 Markdown 渲染
3. 提供“下载”
4. 提供“新窗口打开”

“新窗口打开”不建议直接裸开附件原始链接，而建议走应用内部可控路由，确保格式稳定，例如：

1. 复用现有 `/file-preview`
2. 或新增专门的附件预览路由

这样做的原因是：

1. 原始响应只负责附件内容传输
2. 格式化展示、主题、排版应由前端页面负责
3. 新窗口打开后仍应保持 Markdown 样式，而不是只显示纯文本

## 7.4 日志文件与其他文本文件

日志文件、`.txt`、`.log`、`.json`、`.yaml`、`.toml`、`.md` 之外的纯文本文件，统一进入文本查看器。

文本查看器能力：

1. 等宽字体显示
2. 保留换行
3. 下载按钮
4. 可选的复制按钮

日志文件额外要求：

1. 先以“可查看 + 可下载”为主
2. 大文件不能一次性全量塞给前端

建议首版策略：

1. 预览只加载前 `1MB`
2. UI 明确提示“当前为截断预览”
3. 下载仍下载完整文件

如果后续需要，再追加：

1. 加载更多
2. 尾部查看
3. 搜索

## 7.5 不支持预览的文件

对未知 MIME 或明显二进制文件，统一策略如下：

1. 站内查看器中只展示文件信息
2. 显示“不支持站内预览”
3. 保底提供下载

这样可以保证：

1. 入口统一
2. 行为可预测
3. 不因为错误预览导致乱码或卡顿

## 8. 文件类型判定策略

不能只看文件扩展名，也不能只看 MIME，推荐组合判断：

1. 优先看后端返回的 `mimeType`
2. 再结合文件名扩展名做兜底
3. 最终映射到前端的 `previewKind`

推荐映射：

1. `image/*` -> `image`
2. `text/markdown` 或 `.md/.markdown` -> `markdown`
3. `text/*` -> `text`
4. `application/json`、`application/xml`、`application/x-yaml` 等可安全文本化的类型 -> `text`
5. 其他 -> `unsupported`

说明：

1. Markdown 是文本，但单独作为 `markdown`，因为它的查看器和普通文本不同。
2. 日志文件本质上归入 `text`。

## 9. 后端改造建议

## 9.1 现有接口复用

优先复用现有附件内容接口：

- `GET /api/projects/:projectName/chat-attachments/content`

但建议补两个能力：

1. `download=1`
2. `maxBytes=<number>`

推荐语义：

1. 默认返回原始内容，适合图片和普通文本预览
2. `download=1` 时返回 `Content-Disposition: attachment`
3. `maxBytes` 用于日志和大文本预览截断

## 9.2 安全边界

必须保持已有安全约束不变：

1. 只能访问当前用户、当前项目的临时附件目录
2. 路径必须做 root 限定
3. 不能让前端任意读取系统路径

## 9.3 MIME 与编码

对于文本文件，服务端至少要保证：

1. `Content-Type` 尽量正确
2. UTF-8 文本能稳定读取
3. 编码异常时要 Fail-Fast，不要静默吞错

## 10. 前端改造建议

## 10.1 新增统一附件查看器

建议新增一个站内查看器组件，例如：

- `src/components/chat/view/subcomponents/AttachmentViewer.tsx`

职责：

1. 打开/关闭
2. 根据附件类型选择渲染器
3. 承载下载、新窗口打开等操作

建议再拆三个内部渲染子组件：

1. `AttachmentImageViewer`
2. `AttachmentMarkdownViewer`
3. `AttachmentTextViewer`

## 10.2 消息列表改造

消息项里不要再直接 `window.open(...)`，而改成：

1. 点击附件 -> 设置当前选中的附件
2. 打开站内查看器

图片消息建议保留当前缩略图布局；文件仍保留卡片形式，但卡片点击进入查看器。

## 10.3 Markdown 渲染复用

项目已经有 Markdown 渲染能力，本轮应优先复用，而不是再引一个新的 Markdown 库。

原因：

1. 降低依赖风险
2. 保持聊天内容和附件 Markdown 预览风格一致
3. 便于统一主题和样式

## 10.4 下载能力

下载不要依赖浏览器默认右键或裸链接，而应提供明确按钮。

推荐实现：

1. 查看器内点击下载
2. 前端调用附件内容接口的 `download=1`
3. 浏览器正常保存文件

## 11. 分阶段实施计划

### 阶段 1：图片查看器

目标：

1. 聊天记录内稳定显示图片缩略图
2. 点击图片后进入站内图片查看器
3. 提供下载

预计改动：

1. 消息列表附件点击链路
2. 新增统一查看器容器
3. 图片查看器子组件

### 阶段 2：Markdown 预览器

目标：

1. Markdown 文件站内预览
2. 提供下载
3. 提供新窗口打开

预计改动：

1. 统一查看器增加 `markdown` 分支
2. 复用现有 Markdown renderer
3. 新窗口打开路由或现有预览页复用

### 阶段 3：日志与文本查看器

目标：

1. `.log/.txt/.json/.yaml` 等文本文件可查看
2. 大文件预览可控
3. 支持下载

预计改动：

1. 统一查看器增加 `text` 分支
2. 后端预览接口增加 `maxBytes`
3. 前端增加截断提示

### 阶段 4：不支持预览的文件兜底

目标：

1. 未知文件类型行为统一
2. 至少可下载
3. 不出现空白页或乱码预览

## 12. 风险与取舍

## 12.1 风险

1. 大日志文件直接全量加载会卡 UI
2. Markdown 预览若直接打开原始链接，格式无法保证
3. 如果把二进制文件也硬当文本预览，会出现乱码或崩溃
4. 图片查看器若继续依赖 `window.open`，就无法满足站内查看要求

## 12.2 取舍

本方案的核心取舍是：

1. 先保证图片、Markdown、文本三类预览稳定
2. 对不支持预览的文件，明确只下载
3. 不为了“所有文件都能看”而引入不稳定实现

这个取舍更利于调试，也更符合当前项目“先把主路径做稳”的原则。

## 13. 验收标准

实现完成后，至少满足以下验收条件：

1. 用户发送图片后，聊天记录中能看到缩略图。
2. 点击图片后，在站内打开图片查看器，不新开网页。
3. Markdown 文件点击后能在站内正常渲染。
4. Markdown 文件能下载，且可在新窗口格式化打开。
5. 日志文件和其他文本文件能在站内查看，并可下载。
6. 大日志预览不会导致页面明显卡顿。
7. 未知文件类型不会出现乱码预览，至少能下载。
8. 所有查看动作都保持现有用户/项目隔离，不越权读取附件。

## 14. 建议的下一步

文档确认后，按以下顺序实施最稳妥：

1. 先做站内统一附件查看器壳子
2. 先落图片查看器
3. 再接 Markdown 预览与新窗口打开
4. 最后接日志/文本查看与大文件保护

这样可以尽快把用户最直观的图片查看问题先解决，再逐步把 Markdown 和日志补齐。
