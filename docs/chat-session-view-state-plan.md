# 会话级聊天视图状态改造方案

## 1. 文档目的

这份文档定义“聊天页面内容、输入框、处理中状态、耗时信息、页面页签都跟随会话显示”的专项改造方案。

目标不是先改代码，而是先把下面几件事对齐清楚：

1. 什么状态应该跟随会话。
2. 什么状态继续保持全局。
3. 页面如何做到“按访问加载”，而不是一次把所有页面都加载出来。
4. 新建会话时如何继续保留当前默认的会话模板页逻辑。

## 2. 背景

当前聊天主流程已经具备以下能力：

1. 聊天消息可按会话缓存。
2. 输入草稿和输入模式可按会话缓存。
3. 聊天滚动位置可按会话缓存。
4. 会话处理中、未读状态已有全局链路。

但主内容区仍存在一个结构性问题：

1. `activeTab` 目前是全局状态，不是会话级状态。
2. 切换会话后，聊天内容虽然会切换，但“当前打开的是聊天页、文件页、Shell 页还是插件页”不会稳定跟随会话。
3. 聊天页中的部分实时 UI，例如处理中状态、权限请求、耗时类提示，仍更偏向“当前视图临时状态”，不是“会话状态快照”。
4. 当前页面加载策略是“当前激活哪个 tab 才挂哪个 tab”，但还没有“每个会话有自己的页面状态记录，并且都从同一张会话模板页派生”这一层状态模型。

这会带来几个实际问题：

1. 切换会话时不够直观，容易误以为当前页面属于当前会话。
2. 新会话、临时会话、真实会话替换时，页面状态容易串线。
3. 多会话切换时，聊天区和非聊天页的行为不一致。
4. 后续继续扩展文件查看、插件页、Shell 页时，缺少统一的会话级视图模型。

## 3. 改造目标

本次方案的目标如下：

1. 聊天主页面改为会话级视图状态。
2. 会话 A 和会话 B 可以记住各自最后停留的页面页签。
3. 聊天内容、输入框、输入模式、滚动位置、处理中状态、耗时提示、权限提示等核心元素，都应优先按会话恢复。
4. 新建会话时仍显示当前已有的“会话模板页”，不改变已有新建逻辑。
5. 页面不做全量预加载，只加载当前会话实际打开过的页面。
6. 每个会话第一次进入时，都从同一张会话模板页开始，再按自己的使用轨迹逐步定制。

## 4. 非目标

本轮不做以下事情：

1. 不把所有会话的整棵页面组件都常驻保活。
2. 不重构现有路由结构。
3. 不一次性深度持久化 `files`、`shell`、`git`、插件页的全部内部局部状态。
4. 不修改“新建会话进入空白聊天页”的现有产品逻辑。

原因很明确：

1. 会话级视图状态是本次收益最大的主问题。
2. 如果一上来就做“所有页面、所有会话、所有子状态”的全保活，复杂度会明显失控。
3. 当前最需要先统一的是状态边界，而不是一次做完全部页面状态记忆。

## 5. 当前状态梳理

### 5.1 已经具备会话属性的状态

当前这些状态已经基本具备“按会话隔离”的能力：

1. 聊天消息缓存
2. 输入草稿
3. 输入模式
4. 滚动位置
5. 临时会话与真实会话替换链路

这部分说明项目已经有“会话级聊天状态”的基础，不需要推倒重来。

### 5.2 仍然是全局或半全局的状态

当前这些状态还需要重新收口：

1. 主内容区 `activeTab`
2. 移动端底部导航选中状态
3. 顶部页签选中状态
4. 聊天页里的部分实时运行状态
5. 页面是否已经访问过、是否需要挂载的判断

### 5.3 现有问题本质

问题本质不是“聊天没缓存”，而是“会话状态”和“页面状态”属于两套不同的状态机。

当前更像这样：

1. 路由和选中会话控制聊天内容。
2. 全局 `activeTab` 控制主内容显示哪个页面。

目标则是改成：

1. 选中哪个会话，就读取哪个会话自己的视图状态。
2. 该会话没有自己的视图状态时，再从会话模板页派生。

## 6. 核心设计

### 6.1 会话视图状态模型

建议新增一套会话级视图状态模型：

```ts
type SessionViewState = {
  activeTab: AppTab;
  mountedTabs: AppTab[];
  lastVisitedAt: number;
  chatRuntime: {
    isLoading: boolean;
    canAbortSession: boolean;
    claudeStatus: {
      text: string;
      tokens: number;
      can_interrupt: boolean;
    } | null;
    tokenBudget: Record<string, unknown> | null;
    pendingPermissionRequests: PendingPermissionRequest[];
    startedAt: number | null;
    updatedAt: number;
  };
};
```

这里的设计重点有两个：

1. `activeTab` 负责“当前会话正在看哪个页面”。
2. `mountedTabs` 负责“当前会话已经打开过哪些页面，因此这些页面可以被复用”。

### 6.2 会话视图 Key

建议用下面这组信息构造会话视图 Key：

```ts
${projectName}:${provider}:${sessionId}
```

原因：

1. 同一个项目下可能存在多个 provider 的会话。
2. 单看 `sessionId` 不够稳妥，尤其在临时会话和 provider 并存时。
3. 会话级状态必须和聊天缓存键保持同一类身份语义，避免串线。

### 6.3 会话模板页

这里统一把“新建会话时看到的默认空白聊天页”命名为“会话模板页”。

语义上它是：

1. 项目级默认入口页面。
2. 尚未绑定真实 `sessionId` 的新建对话承载页。
3. 所有会话第一次进入时的默认视图来源。

说明：

1. 文档中的“会话模板页”是产品语义名词。
2. 实现层仍可继续使用 `draft:` 这类内部存储键，不要求因此改动现有代码命名。

无论是第一次进入某个会话，还是点击“新建会话”，都先从这张会话模板页派生默认视图状态：

```ts
const DEFAULT_SESSION_VIEW_TEMPLATE: SessionViewState = {
  activeTab: 'chat',
  mountedTabs: ['chat'],
  lastVisitedAt: Date.now(),
  chatRuntime: {
    isLoading: false,
    canAbortSession: false,
    claudeStatus: null,
    tokenBudget: null,
    pendingPermissionRequests: [],
    startedAt: null,
    updatedAt: Date.now(),
  },
};
```

这正好对应你的预期：

1. 新建会话时还是会话模板页对应的初始聊天页。
2. 不需要把其他页面提前加载出来。
3. 每个会话第一次进入时都像从同一张会话模板页复制一份，再逐步“自己定制化”。

## 7. 页面按需加载策略

### 7.1 基本原则

页面加载策略改为：

1. `chat` 默认属于会话模板页的一部分，因此默认挂载。
2. 其他页面只有在当前会话第一次被打开时，才加入 `mountedTabs`。
3. 当前会话内，已经加入 `mountedTabs` 的页面可以继续复用。
4. 切换到别的会话时，不保留整棵组件树，只保留该会话的视图状态记录。

### 7.2 推荐行为

以会话 A 为例：

1. 初次进入 A，只挂载 `chat`。
2. 用户打开 `shell`，则把 `shell` 追加到 A 的 `mountedTabs`。
3. 用户再打开 `files`，则把 `files` 追加到 A 的 `mountedTabs`。
4. 再切回 `chat` 时，A 的 `chat/shell/files` 属于“当前会话已访问页面”。

切到会话 B：

1. 如果 B 从未打开过其他页面，则仍只挂载 `chat`。
2. 不会因为 A 打开过 `shell/files`，就把 B 也一起加载出来。

这就是“会话模板页派生 + 会话定制 + 按访问加载”的完整语义。

### 7.3 为什么不做全会话 KeepAlive

不建议做“每个会话的所有已打开页面都长期驻留内存”，原因如下：

1. 手机端内存压力会明显上升。
2. `shell`、插件页、编辑器类页面本身副作用较重。
3. 现在最重要的是视图边界正确，而不是先把所有组件永久保活。

因此推荐折中方案：

1. 当前会话内，已访问页面允许复用。
2. 离开当前会话后，仅保存视图元数据，不保留整棵页面树。

## 8. 聊天页跟随会话的状态边界

### 8.1 应跟随会话的核心状态

以下状态应明确归属到会话：

1. 聊天消息
2. 输入草稿
3. 输入模式
4. 滚动位置
5. 是否处理中
6. 中断按钮可用性
7. 状态文案
8. Token / 用量信息
9. 权限请求列表
10. 耗时起点时间

### 8.2 可以继续保持全局的状态

以下状态仍可以保持全局：

1. 浏览器通知开关
2. 深色模式开关
3. 侧边栏展开收起
4. 最近会话列表
5. 全局设置弹层

### 8.3 处理中的会话与后台会话

当前全局已经有：

1. `processingSessions`
2. `unreadCompletedSessions`

这两类全局状态仍然保留，用于：

1. 侧边栏会话状态标记
2. 最近会话条状态标记
3. 未读提醒

但聊天页本身不应只依赖全局集合即时推导，而应同时维护当前会话自己的 `chatRuntime` 快照。

推荐职责划分：

1. 全局集合负责“列表和跨会话提醒”。
2. 会话级 `chatRuntime` 负责“进入会话时立即恢复页面状态”。

## 9. 新建会话与临时会话迁移

### 9.1 新建会话

当用户点击“新建会话”时：

1. 继续进入当前项目的会话模板页。
2. 视图状态从会话模板页创建。
3. 初始只挂载 `chat`。

### 9.2 临时会话 ID

当前存在 `new-session-*` 临时会话 ID。

这部分必须继续兼容，因为真实会话 ID 会在服务端确认后回填。

### 9.3 临时会话转真实会话

当临时会话替换为真实会话 ID 时，除了现有聊天消息和会话选择迁移，还要额外迁移：

1. `activeTab`
2. `mountedTabs`
3. `chatRuntime`
4. 对应的本地存储键

要求：

1. 用户正在临时会话里看的页面不能因为真实 ID 回填而跳回默认状态。
2. 草稿、处理中状态、权限提示不能丢。

## 10. 推荐实施步骤

### 第一步：补会话级视图状态存储

新增一个专用 hook 或 storage 工具，负责：

1. 读取会话视图状态
2. 写入会话视图状态
3. 从会话模板页派生新状态
4. 处理临时会话到真实会话的迁移

### 第二步：把 `activeTab` 从全局改为会话级

改造 `useProjectsState`、`AppContent`、`MainContent` 的数据流：

1. 当前不再只维护一个全局 `activeTab`
2. 改为读取“当前选中会话对应的 `activeTab`”
3. 无会话时回退到会话模板页

### 第三步：把 `mountedTabs` 接到主内容区

改造主内容区挂载策略：

1. 当前会话第一次打开某个页面时再挂载
2. 当前会话未打开过的页面不挂载
3. 新建会话只挂载 `chat`

### 第四步：补齐聊天运行时快照

为聊天视图增加 `chatRuntime` 快照写回：

1. 进入会话时恢复
2. 实时消息到达时更新
3. 完成、报错、中断时收口

### 第五步：补验证与回归用例

至少验证：

1. 会话 A 在 `shell`，会话 B 在 `chat`，切换后能各自恢复。
2. A 的草稿不串到 B。
3. A 的处理中状态不串到 B。
4. 新建会话仍然进入会话模板页。
5. 临时会话转真实会话后不丢页面状态。
6. 没有打开过的页面不会被提前加载。

## 11. 风险与取舍

### 11.1 风险

主要风险有三类：

1. 当前不少组件默认假设 `activeTab` 是全局唯一值，改造时容易漏掉移动端导航、头部 tab 和最近会话切换。
2. `shell`、插件页、编辑器类页面副作用较多，若直接做深保活，复杂度会陡增。
3. 临时会话与真实会话 ID 替换是本次最容易出错的状态迁移点。

### 11.2 取舍

本方案的核心取舍是：

1. 先保证会话级边界正确。
2. 先保证聊天页相关状态恢复正确。
3. 非聊天页内部深状态保活放到后续增强阶段。

这个顺序更利于调试，也更符合当前项目“先稳定、再扩展”的原则。

## 12. 验收标准

文档对应的实现完成后，应满足以下标准：

1. 切换会话时，聊天内容、输入框、输入模式、处理中状态、耗时提示跟随会话恢复。
2. 顶部 tab 和移动端底部导航选中状态跟随会话，而不是全局共享。
3. 新建会话时仍进入会话模板页。
4. 当前会话没有打开过的页面不会被提前加载。
5. 当前会话打开过的页面在该会话内可继续复用。
6. 临时会话转真实会话时，页面状态不丢失。
